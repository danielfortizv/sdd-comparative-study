/opsx:propose tetris-stage2-option-a

Extend the existing Stage 1, option A browser-based Tetris implementation to Stage 2, option A as a brownfield change. Preserve its 10-by-20 board, seven unrotated tetrominoes, left/right/soft-drop controls, collision, locking, line clearing, game over, restart, Python FastAPI backend, React/TypeScript frontend, and in-memory authoritative backend state. Start from this tool's own Stage 1 source and specifications. Create or update this tool's native specification artifacts before changing application code. Use English for all tool interactions, specifications, application text, code comments, and tests. Work only inside this tool's Stage 2 directory.

Add a score, cumulative cleared-line count, level, progressive gravity, one-piece Hold, and one-piece next preview. A new game starts with score 0, lines 0, level 1, and a 500 ms gravity interval. For a lock that clears 1, 2, 3, or 4 rows simultaneously, award respectively 100, 300, 500, or 800 points multiplied by the level immediately before that lock. A lock clearing no rows awards zero. After scoring, add the cleared rows to the cumulative line count and set level to 1 + floor(total_lines / 10). Set gravity_interval_ms to max(100, 500 - 50 * (level - 1)). Soft drop grants no additional points. These numeric rules are study controls, not a request to introduce rotation. The four-line rule may be validated as an isolated domain rule because a four-row clear may not be reachable during ordinary play without rotation.

The backend owns a queued next piece. Every game state response exposes score, total_lines, level, gravity_interval_ms, next_piece, hold_piece (nullable), and can_hold, in addition to the existing board, active piece, status, and ID. Peeking at state never consumes or changes the queued piece. Normal spawning and the first Hold consume the previewed piece and generate exactly one new preview. Swapping with an occupied Hold slot does not consume the preview. A held piece re-enters at the normal spawn origin in its initial orientation, and an obstructed spawn ends the game. Hold can be used once per active piece and becomes available again only after that piece locks. Rejected Holds, movement after game over, and repeated state reads do not mutate game state. Restart resets all Stage 2 counters and Hold state while producing a new active and next piece.

Keep POST /api/games, GET /api/games/{id}, POST /api/games/{id}/tick, and POST /api/games/{id}/move compatible; add POST /api/games/{id}/hold returning the same state shape. The frontend renders score, lines, level, Hold, and next preview from backend state; provides a Hold button and C key; and schedules gravity from gravity_interval_ms while playing. Prevent overlapping requests or stale responses from reversing visible game state. Existing controls and behavior must remain usable.

Do not add rotation, wall kicks, T-Spins, ghost piece, time attack, achievements, persistence, database, authentication, multiplayer, or high-score storage in this stage. Express the new behavior as atomic, testable requirements and explicit acceptance scenarios in the native specs. Implement through the tool's normal spec-driven workflow, with runnable backend tests and a reproducible frontend build. If a defect is found after implementation, first revise the native specification and then regenerate or adjust code through the tool; do not directly patch generated application code. State exact run and test commands, and record any material ambiguity in English.
