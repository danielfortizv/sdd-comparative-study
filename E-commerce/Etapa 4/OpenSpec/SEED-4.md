# Canonical Seed Specification - E-Commerce - Stage 4

## Architectural breaking change: Option A
Migrate the inherited Stage 3 application from a monolithic backend into independently running microservices with real RabbitMQ events. Preserve the working React/TypeScript frontend, Python/FastAPI stack, catalog, cart, authentication, simulated checkout, reviews with images, moderation, caching, automated tests and coverage. This is an architectural migration, not a new set of business features.

## Required migration
- Run at least three independently startable Python/FastAPI business services with explicit ownership boundaries: identity/authentication; commerce (catalog and simulated checkout); reviews (review submission, images and moderation). A thin HTTP gateway may preserve the existing frontend API contract. A gateway must delegate over HTTP, not execute the old monolithic business handlers. More services are optional only if justified.
- Give each service ownership of its state and storage. Separate local SQLite files are sufficient. No shared writable database, cross-service database reads, shared Python singleton state, in-process HTTP transports, or mounting all applications into one process as a substitute for microservices. Shared contract/schema utilities are allowed.
- Use a real RabbitMQ AMQP broker. Integrate it into a business flow: review moderation events update a commerce-owned public review projection and invalidate relevant caches. Pending/rejected reviews remain hidden; approved reviews and their images become public within a documented bounded eventual-consistency window. No in-memory bus or logging-only event demonstration as a substitute for broker integration.
- Document versioned JSON event contracts with event identity, correlation identity, type, timestamp and payload. Use durable queues/messages, publisher confirmation, manual acknowledgements after successful processing, idempotent consumers, bounded retry/dead-letter handling and reconnect backoff. Persist outgoing business events transactionally with domain changes (a small SQLite outbox is sufficient) so a broker outage does not silently lose an accepted moderation change. Do not claim exactly-once delivery.
- Authenticate and authorize internal HTTP operations without trusting client-supplied role headers. Preserve moderator/customer separation, existing demo credentials and frontend-visible behavior. Keep private responses uncached and public projections coherent after events. Keep image visibility consistent with moderation.
- Supply a documented Windows/PowerShell local launch/stop procedure, readiness checks and environment-based service/broker addresses. Read stage4-runtime.json for tool-isolated local ports and AMQP vhost; those are deployment parameters, not different functional requirements. Provide a Compose stack with RabbitMQ, services, gateway and frontend, and update CI, coverage commands and E2E setup for the distributed architecture. No paid cloud services or external deployment.

## Verification and native workflow
First inspect only relevant Stage 3 native specs and implementation, then create all native Stage 4 requirements, architecture/design, API/event contracts and implementation tasks before implementation. Make delegated choices explicitly and concisely. The researcher preauthorizes specs and implementation and accepts reasonable differences between tools; do not ask questions or wait for approvals. All prompts, specs, code, comments, UI and documentation must be in English. Any correction to code must follow a native spec clarification. Preserve earlier-stage and sibling workspaces and do not read or modify external evaluation files.
Verify with meaningful service tests and real multi-process, real-broker integration/E2E tests: purchasing, customer submission, hidden pending review, moderator approval, event-driven public visibility and customer access denial. Prove actual cross-process event propagation; also test duplicate delivery and a broker/consumer outage followed by recovery without losing the accepted change. Test adapters may support focused unit tests but cannot substitute for the real-broker acceptance run. Collect raw backend coverage.xml and frontend lcov.info, run a successful frontend production build, and retain inherited functional checks appropriate to the refactor. Do not invent coverage targets. If Docker is unavailable, validate natively with the provisioned broker and state that container execution is unverified.
Minimize credits: concise specs, targeted file reads, practical tests, no repeated exact-spec audits or unrelated refactors. Stop repeating successful checks unless source changes justify them. Provide exact startup/testing commands and actual limitations in README.md. Finish specs and runnable migrated code.
